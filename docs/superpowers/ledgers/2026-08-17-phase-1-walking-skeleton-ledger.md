# Phase 1 decision ledger — walking skeleton

**What this is.** The running record of every decision made while implementing
Phase 1, written as the work happened rather than reconstructed afterwards.
It is committed because the spec says *what* we built and the plan says *how*,
but only this says **why** — including why several things were deliberately
left undone.

**Read this before Phase 2.** The rulings below are the reasoning behind every
deferral Phase 1 shipped with. The runbook records the user-facing symptoms;
this records the decisions. In particular:

| Deferred | Ruling |
|---|---|
| Transactional outbox — publish-after-commit is caller discipline, not structure | R10, R58 |
| A compile error reports as verdict `IE`; `case_verdict` has no `CE` | R50 |
| The bridge does not verify the judge key; network isolation is the only control | R42 |
| No priority, fairness, or attempt cap — a poison pill re-leases and retries forever | R16, R17 (deferral reversed by R23, which built the watchdog) |
| `DmojDriver.live` keyed by job id alone; cancel narrows the race, does not close it | R66, R71 |
| `SKIP LOCKED` is a throughput property and is untested — the deterministic proof is described | R18, R20 |
| `problem_revisions` has no unique index on `(problem_id, version)` | Task 12 review |

**A note on how to read it.** Roughly a dozen of the defects recorded here were
in the *plan*, not in anyone's implementation — a judge image that was never
published, a config key that hard-exits, a lost-update race in the reconnect
order, an acceptance criterion asserting a guarantee we deliberately never
built. They were caught because implementers stopped rather than making tests
green around them. Where a ruling reverses an earlier one, both are kept; the
reversal is usually the more useful entry.

Format: `Ruling RNN: <decision> — <why> — <what it costs if wrong>`.

## Rulings

Ruling R1: two tasks shipped **Interfaces blocks that contradicted the code in their own task**, and the Interfaces block is precisely what an implementer reads to learn a neighbouring task's shapes. T6 listed `ClaimedJob` without `source`/`languageKey`/`timeMs`/`memoryKb`, which its own `claim()` returns and which T9's worker dispatches from — an implementer building to the block would have produced a job the worker could not use. Both blocks corrected in the plan before dispatch. Cost if wrong: none — the corrections match the code the same tasks already contain.

Ruling R2: T5 defines `languageDriverKeys` (the table that stops judge-server's `CPP17` from becoming our name) but neither mentions it in its Interfaces block nor tests it, while T12 inserts into it. Not fixed in the plan text — instead T5's dispatch requires a test asserting the mapping round-trips, and T12's dispatch names the table explicitly. Why not edit the plan: the table's definition is already correct and complete; only its verification was missing. Cost if wrong: T12 discovers a column mismatch and reports it.

Ruling R3: **`Worker` had no test**, and it is where a lapsed lease becomes a `driver.cancel` — the mechanism that stops an abandoned grade from burning judge capacity, and one of the phase's stated safety properties. Shipping it on the strength of the config tests alone would leave the single most consequential loop in `judged` unverified. Added a required step to T9 with two tests (happy path, and cancel-on-lapsed-lease), plus a small refactor extracting `heartbeatOnce()` so the test drives the logic rather than waiting 20 seconds of wall clock. Cost if wrong: one extra public method on `Worker` and a slightly larger T9.

Ruling R10: **the implementer is right and my brief overstated the guarantee.** `EventWriter.apply()` calls `write()` then `publish()`. Nothing ties publishing to a COMMIT — only to `write()` returning. My comment claimed publishing inside a transaction "is a call that cannot be made"; in fact the code enforces it as a caller convention, and test 5 deliberately violates that convention by wrapping `apply()` in `db.transaction` and throwing. The write rolls back via savepoint; the publish already fired.
Ruling R10 (what is actually true): in the real code path the worker calls `apply()` per event with no enclosing transaction, and each `write()` is a single auto-committed statement — so publish-after-write IS publish-after-commit in production. The guarantee holds where it matters. What does NOT hold is survival of a caller-managed outer transaction, which is a scenario the worker never creates.
Ruling R10 (resolution): keep the implementation as the brief has it, and **fix the test and the comment instead of the code**. Test 5 becomes "a failed write publishes nothing" — make `write()` fail for real (a constraint violation) and assert `publish` was not called. That is the property the design genuinely provides and it is worth guarding: a write that throws must not announce state that was never stored. The overstated comment is corrected to state the real invariant and name the unsupported case. Cost if wrong: the suite guards a slightly narrower property than my comment originally advertised — which is the honest position rather than a weakened one.
Ruling R10 (deferred, recorded for a later phase): the STRONGER guarantee — publish surviving an arbitrary caller-managed transaction — requires the transactional outbox pattern: write the event and an outbox row in one transaction, with a separate poller publishing from the outbox, so a rollback removes the intent to publish along with the state. That is the textbook answer and genuinely correct, but it adds a table, a poller and delivery-marking, which is real scope against a hazard the current caller cannot trigger. Recorded rather than smuggled into Phase 1.
